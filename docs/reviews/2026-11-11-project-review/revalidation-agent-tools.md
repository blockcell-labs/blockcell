## B2-01：记忆读取范围与 shell 沙箱必须一致

真实入口存在：`auto_memory/extractor.rs:254`、`:685` 和 `scheduler/consolidator/consolidate.rs:40` 设置记忆工作目录及记忆范围的 can_use_tool，仅从 schema 排除 exec，shell 仍可被调用。`forked/can_use_tool.rs:796` 先判只读命令，再验证工作目录与字面 token；`:846` 不解析 operand 的真实文件系统位置。`forked/agent/tool_exec.rs:520` 再次校验的仍只是工作目录，最终使用 `WorkspaceWrite`（`:237`）。

已核对补偿防线：直接文件工具的范围检查不适用于这个 shell operand；危险命令模式也不拒绝普通读取。Seatbelt 的普通文件读取许可及 bubblewrap 的全盘只读绑定允许读取普通目录外文件。后台代理并非因此获得任意凭据读取能力：固定敏感目录禁止规则、文件系统权限、平台后端可用性仍会影响结果。原结论应保持“目录内已有链接指向普通可读外部文件”的前提，不扩写成所有平台必然可读取任意文件。

修复边界：优先为记忆 fork 使用已有的受约束文件能力；若保留 shell，需要实现与记忆目录一致的读取范围，而不仅是写入范围。单独给 token 增加 canonicalize 仍不能覆盖递归遍历、shell 语法和检查后路径变动。自动记忆与梦境整合两个入口应共享同一修复，且不能误伤合法记忆写入工具。

验收条件：合法目录内读取保持可用；目录内链接指向外部哨兵、递归遇到外部链接时均不能把外部内容交给模型；绝对路径、上级目录及工作目录逃逸仍拒绝。分别验证受支持原生后端的实际读范围，未支持的安全边界应拒绝执行。不要只断言字符串谓词返回值。

## B2-02：技能遗漏的是证据消费和续轮行为

`runtime/turn_flow.rs:388` 创建 TaskProgress，并注册消息及工具携带的契约；`:464`、`:516` 继续合并契约。但技能循环没有调用 observe，也没有使用 needs_verification 或 first_incomplete_output；无工具响应直接结束，返回时仅生成后续会话契约（`:556`）。`runtime/skill_session.rs:40`、`:102` 的契约传递和持久化不能替代本轮检查。手动/路由技能在 `process_message_inner.rs:535` 提前返回；activate_skill 分支在 `:1491` 接受技能回答并跳出主循环。

原报告应收窄：普通循环的验证分支受配置及契约允许执行与否控制，并由 verification_gate_fired 限制；交付物提示也只发送一次（`:2155`、`:2191`）。因此这里不能表述为“普通路径保证完成、技能绕过强制成功条件”。准确后果是：相同任务契约在技能路径缺少普通路径已有的补验/补产物提示及证据状态更新，能更早交付缺少验证或产物的回答。系统并未伪造通过的测试记录。

修复边界：抽取共同的证据观察及结束决策，覆盖技能内工具、手动技能及 activate_skill 三条路径；保留每步实际 revision、后台进程完成证据和验证结果，不可仅检查历史中是否出现过测试工具名。技能应采用宿主配置的 verification policy，继续尊重 Forbidden/Deferred、交互模式和预算边界。已有上层激活前的证据状态也需要明确如何继承，避免重建 TaskProgress 丢失信息或重复验证。

验收条件：同一显式契约分别走普通循环、手动技能和 activate_skill，验证其补验及缺失/未更新交付物提示一致；成功验证后再次修改应要求新的适用验证；验证失败不能显示为通过；禁止或延后验证的契约不启动验证。若继续采用有限次提醒，最终未满足条件的回答应保留准确状态，测试不得假设现有实现是硬完成门。

## B2-03：预算权威状态不能作为普通缓存驱逐

`runtime/turn_flow.rs:127` 在新会话且表长达到 64 时删除 HashMap 的任意现有 key；`:133` 使用 BudgetTracker::with_parent 重建。`core/budget.rs:128` 初始化 token、成本计数为零。模型请求前检查（`turn_flow.rs:278`）和响应记账（`:204`）均重新查表，没有从审计或会话元数据恢复累计值。`runtime.rs:3320` 附近的消息派生会共享状态，问题适用于长生命周期服务。

保留中的 Arc 不会替当前映射自动恢复数据；子任务仍可能向旧父 tracker 记账，而同一个父会话已经取到新的 tracker，因此修复还要防止并存的两份账本。子 agent 的 parent_budget 可以继续限制该子链路，不能据此声称所有层级预算一起重置；顶层 runtime 的 parent_budget 为 None，仍直接受影响。旧标题应读作“一个被驱逐旧会话的计数在重建时归零”。

修复边界：分离有限热缓存与累计消费账本，驱逐应可无损恢复，或保留有额度约束会话的权威 tracker；处理活跃请求、父子预算归并和上下文窗口估计的身份一致性。避免通过扩大缓存阈值掩盖问题，也不要把一次上下文压缩等同于重置累计账单。

验收条件：超过 64 个历史会话后，已耗尽会话再次请求仍被拒绝；未耗尽会话保留 token 和成本累计值；活跃请求及子任务在驱逐附近完成时，用量只计一次且落入同一权威账本。预算未配置时可保持既有无限额语义。

## B2-04：统一 account、session、agent 的任务归属

`task_manager.rs:102` 的 belongs_to_origin 只比较 channel/chat；`:985`、`:1373` 的查询及 OriginScopedTaskManager 继承同一比较。`runtime/tool_pipeline.rs:1197` 只传入这两个字段，虽然 spawn handle 及 TaskInfo 已持有 origin_account_id、origin_session_key、agent_id。多账号渠道会保留 account_id，而 canonical session key 会区分账号，这些信息确实在授权处丢失。

扩展范围：`bin/blockcell/src/commands/gateway.rs:828` 创建共享 TaskManager，`:1167` 至 `:1176` 向各 agent runtime 传入 clone，`:465` 注入运行时。因此同 channel/chat 的不同 agent 也会相互看到或控制任务，不能把问题限定为单 agent 双账号。宜合并扩展 B2-04，不重复编号。

自动结果混入有额外条件：`process_message_inner.rs:2248` 必须先找到匹配的运行中 typed task，且当前预算未耗尽，才进入等待/汇总；随后 `:2304` 选择尚未注入的完成结果。仅有外来已完成任务、没有匹配运行中 typed task，不会单独触发此分支。工具列表、详情、取消、发送任务消息及 `/tasks` 则另有直接访问入口。

修复边界：以不可变的完整 origin 身份统一查询和操作授权，至少包含 canonical session key 与 agent；不要仅在工具列表做过滤。主消息任务当前经 `runtime/run_loop.rs:370` 的旧创建接口进入，account/session 默认为空，必须一并补齐。检查点虽保存 session_key，却仍在 `checkpoint.rs:74`、`:180` 按 channel/chat 授权，续跑与任务管理需同步修复。旧持久化记录身份不完整时应明确拒绝或显式迁移，不能回退到弱匹配。

验收条件：同 channel/chat、不同 account 或 agent 的任务在列表、详情、取消、任务消息、前缀查找、自动汇总、检查点枚举及恢复时全部隔离；本来源的操作与取消幂等性保持可用；创建、持久化、重启恢复后身份一致。跨来源失败应按不存在处理，避免通过错误信息泄露任务内容。

## B3-01：Rhai 的嵌套授权不等同于宿主授权

活动入口是 `exec_skill_script.rs:270` 的 Rhai 分支，不依赖 deprecated 的旧脚本 helper。它从技能 meta.yaml 读取声明工具，使用 NestedToolGuard，再通过新建 registry 执行（`:278` 至 `:304`）。NestedToolGuard 检查 toggles、ToolPolicy、危险操作及 FullAccess shell（`tool_guard.rs:346`），没有宿主 PathPolicy 或本会话路径批准状态。默认 ToolPolicy 缺文件时为 Allow；显式 Deny/Ask 规则可以阻断相应嵌套调用，因此前提仍需保留“工具策略没有额外阻断”。

已核对确认路径：Rhai 的 execution_environment 为 FullAccess，但 requires_confirmation 返回 false（`exec_skill_script.rs:131`、`:143`）；宿主 `tool_pipeline.rs:871` 明确按 requires_confirmation 判定，环境标签本身不构成防线。外层 `path_security.rs:585` 只检查技能脚本路径是否安全相对路径。ReadFileTool/WriteFileTool 的默认必需权限为空，LocalFilesystem 直接进行本机文件操作，registry 的 PermissionSet 检查不能补齐具体路径授权。技能声明工具名也不能表达具体资源授权。

修复边界：给嵌套 dispatcher 注入宿主的资源授权及执行能力，或使用事先限定范围的文件 backend；禁止、未知和需交互批准但当前不可交互的路径应拒绝。保持工具策略、禁用开关、审计、路径策略和账号/会话上下文一致。修复不能只覆盖单路径读取，遗漏多文件读取、批量写入及其他会写文件的工具；也不宜另造一套敏感文件名黑名单。

验收条件：相同人工 deny 哨兵路径在直接文件工具与 Rhai 嵌套工具中均拒绝；未批准的外部路径不能获得写权限；已允许范围内的合法工具调用保持可用；显式 ToolPolicy Deny/Ask、禁用工具、未声明工具仍拒绝。失败路径应留下准确审计，不能把被拒绝操作报告为成功。

## B3-02：ZIP 目标侧链接检查是独立缺口

`file_ops.rs:588` 拒绝归档条目的链接模式，mangled_name 也会处理归档路径，但二者都不能约束目标文件系统中的既有链接。`:596` 至 `:604` 对拼接后的目标直接创建父目录、创建文件并复制；父目录链接与叶文件链接均会被普通文件 API 跟随。外层只检查 destination 根目录（`path_security.rs:273`），不会检查具体产物。FileOpsTool 声明 WorkspaceWrite，但实际解压经宿主 spawn_blocking 执行（`file_ops.rs:182`），没有原生写沙箱补偿。

结论限定为当前 ZIP 实现，前提是已有目标侧链接、目标在宿主文件权限下可写及根目录准入通过；无需归档包含链接条目或上级目录路径。不把 tar 的 unpack_in 实现自动视为同样存在缺陷，也不把此前文件操作原语检查描述成完整解压工具实测。

修复边界：解包时逐目标拒绝链接组件，并用固定目录句柄及不跟随链接的文件创建策略防止检查后替换。全新隔离目录解包后安全合并也可，但合并阶段必须维持同样边界。归档条目限制、条目数/大小/压缩比限制应继续生效；仅 canonicalize 一次 destination 根目录不足。

验收条件：目标父目录链接、目标叶链接及目录替换竞争均不能修改外部人工哨兵；正常目录可以解包；归档内链接、特殊文件、路径越界及资源限额拒绝行为仍有效。失败应明确返回，临时资源可清理，不得宣称整个解包具备尚未实现的事务性。

## B3-03：列表身份与管理目标需形成明确接口

`tools/skills.rs:350` 优先使用标准技能的 frontmatter name，返回值同时包含物理 path。`SkillViewTool` 和 `SkillManageTool` 只把 name 原样交给 SkillFileStore。后者在 `skill_file_store.rs:120` 优先按相对目录寻址，再在 `:837` 附近按目录 basename 搜索；没有标准 frontmatter 身份映射。目录名不同的标准技能是已支持布局，因而不是非法安装输入。返回 path 允许人工推断目录，但没有使 name 契约一致。

修复边界：明确稳定技能身份与管理目标 ID，选择让列表返回可直接使用的目标 ID，或让管理解析共享同一身份索引。对于重复 frontmatter 身份、目录名与另一身份碰撞、分类技能，必须返回明确歧义，避免查看/修改错误技能。保留现有相对路径、符号链接及路径组件校验。

验收条件：目录名不同、分类路径、标准技能、原生技能都能从列表结果直接查看和管理；重复身份不会静默选中错误目录；内置技能与 workspace 技能的可写范围及覆盖优先级保持明确；外部路径、隐藏内部目录仍不可成为管理目标。

## B3-04：快照不应参与已安装技能发现

`skill_file_store.rs:519` 保存完整技能目录到 `.snapshots`；`tools/skills.rs:318` 的排除表没有该目录，普通分类递归会进入其中。快照保留的技能标识会被当作已安装内容。标准格式还使用原 frontmatter name 参与 seen 去重；read_dir 未排序，所以“旧快照覆盖现行列表说明”是可能行为，不能断言每次都发生。`skills/manager.rs:956` 的实际加载器只递归 manifest 技能包，不会以同样方式加载普通快照目录，因此列表与实际可激活集合会分离。

修复边界：优先共享技能发现规则或索引；至少明确排除快照、锁及临时目录，并确保内部目录不参与身份去重。不要通过删除快照解决列表污染，快照还承担撤销功能。不能简单把“所有点号目录”与技能业务规则混为一谈而意外隐藏合法布局。

验收条件：创建、修改、删除、撤销后列表与实际可激活集合一致；快照路径从不出现，旧元数据不抢占现行身份；撤销仍能使用保留的快照，现有保留数量限制继续有效。测试不依赖文件系统枚举顺序。

## B3-05：失败下载要保留旧文件

`bounded_io.rs:57` 在读取响应前打开目标并截断；读取错误通过 `?` 返回，已写前缀留在原路径。超限返回 truncated 后，`http_request.rs:445` 删除该路径。既有路径已获写授权不代表调用方接受失败时丢失旧版本。恰好达到大小上限的响应会被接受，不能把“等于限额”列为失败条件。

修复边界：在同目录创建唯一临时文件，完整读取并满足工具既有成功标准后替换目标，任何失败仅清理本次临时文件。保持成功响应的 status/headers/bytes_saved 协议和现有 HTTP 状态处理语义；是否持久化非 2xx 响应不应在这个修复中被无意改变。同时处理刷新、替换失败和并发下载的文件命名/提交语义。

验收条件：预置人工哨兵后，响应读取中断、超时、超限、写入或最终提交失败均保留旧内容；成功下载完整替换；不存在目标时失败不留下假成品；恰好大小上限仍成功；失败不遗留本次临时文件。无需通过真实外部服务或大型响应验证这些行为。

## N01 [P1]：省略解压目标时未授权隐含写目录

这是与 B3-02 不同的遗漏，不依赖符号链接。`file_ops.rs:552` 至 `:557` 在 destination 缺失时选择归档父目录作为写目标。`path_security.rs:273` 至 `:280` 仅把解压 path 登记为 Read，只登记显式 destination 的 Write；没有登记这个隐含目标。FileOpsTool 是宿主进程操作，WorkspaceWrite 标签不施加文件系统隔离，危险操作检查也没有为普通解压补出目标写授权。

前提与后果：归档处于工作区外、其读取被允许或单独批准，而该父目录写入尚未批准或被策略拒绝。省略 destination 后，主管线只完成归档读取准入，工具仍会在父目录生成产物。即便配置对父目录写入为 Deny，也没有对应 Write access 进入判定。源文件可读与目标目录可写是两个独立权限；不应将读取批准解释成解压写批准。

修复边界：参数规范化时统一解析有效解压目标，并把它作为 Write access 交给既有 PathPolicy、会话授权和交互批准流程；显式与默认目标必须采用同一语义来源，避免工具执行和授权提取再次分叉。结合 B3-02 的逐产物安全处理，默认目标授权也不能取代链接与后代路径检查。ZIP 与 tar 各格式都需要覆盖，因为默认目标解析在格式分流之前。

验收条件：外部人工归档读取允许、父目录写入拒绝时，省略 destination 必须在创建任何产物前失败；只有读批准时应单独请求写批准，非交互场景应拒绝；父目录写批准后方可执行。显式目标与默认目标的授权行为一致，正常工作区内解压保持可用。回归应验证授权决策和实际产物两端，不以单独调用解压函数证明完整准入有效。

## 修复顺序与覆盖边界

先修路径授权共享（B3-01）、ZIP 目标处理（B3-02/N01）及完整任务归属（B2-04）；后台记忆读范围（B2-01）需要按支持的平台验证。随后修预算账本、技能续轮、技能发现与管理身份、下载提交语义。上述问题可在明确边界下分批修复，但公共授权、归属及发现逻辑应尽量共用，避免调用路径之间再次分叉。

本轮没有对生产模型、真实 IM、真实凭据、真实外部网络或全部原生沙箱做端到端验证；尚无证据否定原九项缺口，也不把静态调用链视为高并发、跨平台及完整产品行为的全部验证。
